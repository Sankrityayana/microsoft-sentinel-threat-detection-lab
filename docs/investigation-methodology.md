
# Incident Investigation Methodology

## 1. Overview

This document describes the investigation workflow followed in the Microsoft Sentinel lab.

The objective was to investigate alerts generated by scheduled analytics rules, examine their underlying Windows security events, identify the activity responsible for each alert, and record an evidence-based conclusion.

## 2. Investigation Lifecycle

The lab followed this workflow:

1. Alert generation
2. Incident identification
3. Alert and incident review
4. Underlying event retrieval using KQL
5. Examination of event attributes
6. Correlation with controlled test activity
7. Classification and investigation notes
8. Incident resolution

## 3. Alert Triage

For each generated incident, the following information was examined:

- Alert name and severity
- Incident status
- Detection rule
- Affected computer
- Associated account
- Event identifier
- Event timestamp
- Caller process or source IP, where applicable
- Related event details
- MITRE ATT&CK mapping

## 4. Evidence Collection

The underlying SecurityEvent records were queried in Log Analytics.

Evidence fields examined included:

| Field | Investigation purpose |
|---|---|
| TimeGenerated | Establish event time |
| Computer | Identify the reporting host |
| EventID | Identify the Windows event type |
| Account | Identify the associated account |
| EventRecordId | Reference the specific event |
| IpAddress | Examine the reported source address |
| Process | Examine process context |
| EventData | Extract event-specific information |

Not every field is populated in every event type.

## 5. Classification

The lab used the Sentinel incident classification and determination workflow.

For CASE-14 and CASE-29, controlled test activity was recorded as:

- Classification: Informational, expected activity
- Determination: Security testing

For CASE-28, the alert details page confirmed Classification = Informational, expected activity, and the alert activity history recorded Determination = Security testing. These are alert-level fields and should be distinguished from separate case-level summary metadata.

Classification was based on the controlled test procedure and the corresponding event evidence where the values were confirmed.

## 6. Investigation Documentation

Each investigation report should record:

1. Incident identifier
2. Detection rule
3. Alert severity
4. Event evidence
5. Investigation timeline
6. Controlled test procedure, if applicable
7. Findings
8. Classification and determination
9. Analyst comments
10. Final incident status

## 7. Investigation Principles

- An alert is an investigative lead, not proof of compromise.
- Event context must be examined before drawing conclusions.
- Controlled tests must be identified explicitly.
- Missing evidence must not be interpreted as proof that activity did not occur.
- Conclusions must remain within the limits of the available telemetry.
- Investigation notes should be clear enough for another analyst to review.

## 8. Scope and Limitations

The investigations in this repository concern controlled activity on a single Windows Server lab VM.

They demonstrate a basic SIEM investigation workflow, not a full enterprise incident response process.

The lab does not establish production SOC experience, enterprise-scale monitoring, or forensic certainty.
